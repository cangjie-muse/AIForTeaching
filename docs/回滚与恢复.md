# 回滚与恢复

结论先说：**代码随时能回滚，数据库不能靠 git 回滚。**
这两件事必须分开处理，否则最容易出的不是"回不去"，而是"以为回去了"。

## 1. 代码回滚：三种方式，选错会丢东西

| 场景 | 命令 | 说明 |
| --- | --- | --- |
| 已推送/别人已经在用，要撤销某次提交 | `git revert <提交>` | 新增一个反向提交，历史保留。**共享仓库只能用这个** |
| 本地未推送，想彻底抹掉最近的提交 | `git reset --hard <目标>` | 历史真的消失，不可恢复 |
| 只想撤一个文件的改动 | `git checkout <目标> -- 文件路径` | 其余改动不动 |

### 本仓库当前状态（2026-10-21）

```
HEAD          32ffec9  test: 把后端真正跑起来
标签          stage-api-config  ← 已验证通过的状态，随时可以回来
               v0.11.0
未推送        13 个提交（remote 停在 97c0f50）
```

因为**全部 13 个提交都还没推**，`git reset` 在这里是安全的——没有别人的副本，
不存在"我改写了历史导致别人冲突"。

但要清楚它的反面：**没推 = 只在这台机器上**。硬盘坏了就全没了，
git 回滚能力再强也救不回来。这是目前唯一真正的风险。

### 回到"上次全部通过"的状态

```bash
git status                        # 先确认没有未提交的改动
git reset --hard stage-api-config # 回到已验证通过的版本
npm run check && npm run test:api # 重新验证
```

如果只是"某个提交不对，但后面的提交想留着"：

```bash
git log --oneline -10             # 找到要撤的
git revert <提交号>                # 反向提交，后面的历史都在
```

刚才我实际演练过一次：在临时分支上故意提交一个错误文件，`git revert` 之后
工作区与 `stage-api-config` 的差异是 **0 行**。演练分支已删除，`main` 未受影响。

## 2. 数据库：git 回滚不了，这是设计选择

`db/migrate.py` 是**只前滚、无回滚**的，六个迁移文件里也没有任何 `-- DOWN` 段。
这不是漏写，是有意的：

- 迁移一旦在某个环境执行过，它就是**历史**。写 down 脚本意味着要写一份
  "反着做"的 SQL，而它本身也是代码，也会错。
- 更常见的做法是**前滚修复**：发现 0006 有问题，就写 0007 去改，
  而不是把 0006 撤掉。这样任何一个环境的 `schema_migration` 表都只有一条路径。

### 好消息：现有六个迁移全是"新增式"

我核对过，没有 `DROP TABLE` / `DROP COLUMN` / `ALTER COLUMN TYPE` / `TRUNCATE`：

```
0001 建表 26  加列 0  视图 5
0002 建表  7  加列 2  视图 0
0003 建表  1  加列 5  视图 2
0004 建表  1  加列 0  视图 1
0005 建表  0  加列 2  视图 1
0006 建表  0  加列 6  视图 1
```

这意味着：**回滚代码、保留数据库是安全的**。旧代码不认识新列，只是不用它们，
不会报错。这是新增式迁移的最大好处，也是应该继续保持的习惯。

### 真正危险的操作

- 改一个**已经应用过**的迁移文件 → `migrate.py --status` 会报"被改动过"并拒绝执行。
  这是保护，不是障碍。
- 手工在库里 `DROP COLUMN` → 下一次 `--apply` 不会察觉，但代码会 500。
- `DROP SCHEMA` / 删库 → 只有快照能救。

### 数据错了怎么恢复

| 情况 | 办法 |
| --- | --- |
| 还没上线（现在） | 直接重建：`python db/migrate.py --apply`，数据本来就可以从 `data/*.json` 重生成 |
| 上线后、误删少量数据 | 从备份恢复到临时库，只把需要的行导回来 |
| 上线后、迁移把数据改坏了 | 停止写入 → 恢复快照 → 写一个 0007 修正 |

所以**上线前第一件事是配好备份**，而不是配监控。备份没做好，任何回滚都只是心理安慰。

## 3. 不在 git 里的东西，回滚拿不回来

| 内容 | 位置 | 能否靠 git 回滚 |
| --- | --- | --- |
| 模型 API 密钥 | `secrets/*.key`（已 gitignore） | ❌ 删除即丢失，需重新填 |
| 环境变量 | `server/.env` | ❌ 只有 `.env.example` 在库里 |
| 数据库数据 | PostgreSQL | ❌ 只能靠快照 |
| 生成的报告 | `reports/*.json` | ✅ 可重跑 `npm run check` 重建 |
| 课程数据 | `data/*.json`、`course-packs/` | ✅ 在库里，可以回滚 |

密钥那条最容易被忽略：回滚代码不会把密钥"回滚"回来，反之清掉密钥也不会被
git 恢复。**密钥的唯一副本在服务器文件系统和你的密码管理器里。**

## 4. 上线后的标准回滚流程

```bash
# 1. 先停流量，避免回滚过程中新旧代码同时写库
# 2. 判断是代码问题还是数据问题
#    代码问题 → 下面第 3 步；数据问题 → 跳到第 4 步
# 3. 回滚代码（已推送，所以用 revert）
git revert <有问题的提交>
npm run check && npm run test:api
# 4. 数据问题 → 恢复快照，不做代码回滚
# 5. 两种都要：回滚后跑一次健康检查，确认模型端点还在
curl http://127.0.0.1:8000/api/v1/health
```

第 5 步容易被跳过。`/health` 返回的 `models` 字段会告诉你当前用的是哪个端点、
数据出不出校。回滚后如果这个字段变了，说明环境变量也变了，那才是真正的麻烦。
