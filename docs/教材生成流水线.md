# 教材生成流水线

老师上传教材 PDF，平台切章、排队调用模型，生成**知识点 + 习题**并进审核队列。
这一页说明它怎么跑、边界在哪、哪些地方还没验证。

## 两种模式

- **整本（默认）**：老师只上传 PDF。平台按章标题切开（`第X章` / `Chapter N` / `§N`），
  每章一个子任务，逐章生成；某章失败只重跑那一章。
- **单章**：自己填 PDF 页码范围。用于校准切章、或只补某一章。

## 链路

```
老师：上传 PDF（教材生成页）
  → POST /api/v1/textbooks                原始字节，落 uploads/<sha256>.pdf，顺手探测页数与文字层
  → GET  /api/v1/textbooks/{id}/chapters   切章预览：会切成几章、每章几页、依据是标题还是页窗
  → POST /api/v1/textbooks/{id}/generate-book   入队 pipeline_job(kind='generate-book')
  → worker：python scripts/run_worker.py
      0. 父任务切章：为每章建一个子任务（同一父任务同一章只建一次）
      1. 子任务取该章文字（textbook.text_path，没有就用 pypdf 抽一次并存下）
      2. 拼 prompt，调模型（一章一次调用）
      3. 校验模型输出：知识点必须有正文，题目必须挂得上知识点，页码不能跑出本章
      4. 落库：chapter / knowledge_node / exercise，provenance 由代码判，review_status='draft'
      5. 写资源包：course-packs/<课程>/generated/job-<id>/{知识点.md,习题.md,知识节点.json,生成说明.json}
  → 审核页：这些题出现在队列里，人工过一遍才发布
```

单章模式把 0、1 换成"按给定页码范围取文字"，其余相同。

## 切章规则（切错一章，整章溯源都会偏）

1. 只认**每页前 12 个非空行**里的独立短行（≤40 字，不以句号/逗号结尾）。
   正文里"见第 1 章"这种句子到处都是，把它当标题会把书切成碎片。
2. 同一章号再次出现不再计数——教材页眉每页都印"第 1 章 实数"，那不是新章。
3 找不到两个以上标题就退回"每 15 页一章"，并明确告诉老师"这是猜的，建议先校准"。
4. 一本书最多 40 章，超出部分并入最后一章，并在预览里说明。

## 断点续跑

- 子任务按 `(parent_id, chapter_key)` 唯一：重跑整本**不会**新建子任务、**不会**重复出题。
- 失败章：`POST /api/v1/jobs/{id}/retry` 只把失败的章重新排队，已成功的章不动。
- 父任务只有在所有章都有结论时才给终态：全成功 → succeeded；有任何失败 → failed，
  并在 `result.failed` 里列出是哪几章、错在哪。

## id 规则（为什么带 chapter_key）

生成物的 id 是 `gen-<chapter_key>-<标题哈希>-001`，章 id 是 `<chapter_key>-<标题哈希>`。
**必须带 chapter_key**：教材里两章同名（比如两个「习题课」）是正常情况，只用标题哈希会让
后一章的题覆盖前一章的题——数据上看不出错，只是第一章的题凭空消失。

## 为什么拆成这么多步

`prompts/Course-Building-Standalone.md` 是给**智能体**的：它要求读 PDF、翻页核对、写 xlsx。
一次对话调用给不了这些能力。拆开之后职责是：

| 谁 | 负责什么 |
| --- | --- |
| 代码 | PDF → 带页号文本、切章、书页/PDF 页换算、id、溯源标签、xlsx |
| 模型 | 这一章有哪些知识点、每道题的题干与解答 |

这不是把提示词削弱了，而是把**机器可读字段从模型手里拿走**。现有 4807 道题里
809 条溯源无法判定、1270 条没有精确页码，追根都是让模型写书目信息：它写
"主教材习题一·2"，导入器只能猜。现在书页由代码从真实 PDF 注入，溯源按
"有没有教材原题号"判定，这类噪声在生成端就不会出现。

## 跑一次

```bash
# 1. 建表
.venv/bin/python db/migrate.py --apply

# 2. 装抽文字的依赖（纯 Python，不需要 poppler）
.venv/bin/pip install -r server/requirements.txt

# 3. worker 常驻（服务器上装成服务，见下一节）
sudo systemctl enable --now whu-worker

# 4. 打开平台「课程内容 → 教材生成」，选课程、上传 PDF；整本模式先给切章预览，确认后开跑
```

## worker 为什么要装成服务

`whu-worker.service` 跑的是 `scripts/run_worker.py`：它从 `pipeline_job` 领任务、
一章一次调模型、写完落库。**不装它，上传 PDF 后任务会排队但永远不动**，
页面上只看到"排队中"，看起来像平台坏了。

```bash
sudo cp deploy/whu-worker.service /etc/systemd/system/
sudo systemctl daemon-reload && sudo systemctl enable --now whu-worker
systemctl status whu-worker --no-pager     # 看 active (running)
journalctl -u whu-worker -n 50 --no-pager  # 卡住时看这里
```

`deploy/update.sh` 会顺带重启它；worker 没装时那一步会跳过并提示，不会中断更新。

## 生成出来的资源包为什么不能直接再导入

落库之后还会在 `course-packs/<课程>/generated/job-<id>/` 写一份
`知识点.md`、`习题.md`、`知识节点.json`——那是**按章留档**，不是整包：

- 一份只有一章，而导入器要求一个课程级（一级）节点；
- `知识节点.json` 的第八列是标签，不是 `知识点.md#…` 的锚点引用。

要把它变成可导入的整包，用「导出三件套」把整门课导出来改，不要拿生成目录直接导。

开发期没有模型 Key 时，`DEV_FAKE_MODEL=1` 会走演示模型：结构真实、内容是占位，
任务照常入库进审核，用来打通链路。生产环境禁止该开关（`main.py` 会拒绝启动）。

## 边界与未验证项

- **扫描件没验证过。** 上传会显示"无文字层"，但 OCR 链路（`pipeline_job.kind='ocr'`）
  还没接。扫描件目前会失败在"这一章没有抽到文字"这一步，错误信息是明确的。
- **PDF 解析依赖 `pypdf`。** 这个环境装不上（无网络），所以测试走的是"已经抽好的文本"
  这条路径；`probe_bytes` 不依赖任何库，页数与文字层探测是真跑过的。
- **整本目前是串行跑**（worker 一次一章）。并发跑要处理同一个课程的行锁与 xlsx 写冲突，
  先不动。
- **没有自动重试的退避。** `attempts` 有记录，重试要手动点（页面和接口都支持）。
- **生成结果不会自动出现在学生端。** 学生端读的是课程包静态数据，生成结果只进数据库和审核队列；
  发布流程（导出到 `data/`）还在设计。

## 成本

一章一次调用（约 1.2 万字上下文，输出 3–8 千字）。按 DeepSeek 的公开价格，
一章在几分钱到一毛钱之间；一本书十章不到一块钱。真正的成本是**人工审核**。
