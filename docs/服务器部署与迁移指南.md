# 服务器部署与迁移指南

日期：2026-10-20。回答三个问题：**现在搭的框架搬到服务器上好弄吗？服务器上要改什么格式？为了以后做问答和 AI 学伴，现在必须定什么？**

## 0. 结论先说

**好弄。** 现在这套东西的可移植性是这样的：

| 部分 | 搬服务器要做什么 | 工作量 |
| --- | --- | --- |
| PostgreSQL 表结构 | 直接用 `python db/migrate.py --apply` | 零 |
| 现有 14 门课数据 | 重新跑 `build_seed.py` + `seed.sql` | 零 |
| FastAPI 代码 | 改环境变量即可 | 零 |
| Docker Compose | 直接起 | 零 |
| 教材文件存储路径 | **要抽象**（现在隐含"本地目录"） | 小，已留设计 |
| 身份认证 | **要接**（现在 `X-Actor` 头可以随便伪造） | 中 |
| embedding 维度 | **现在就要定模型** | 一旦灌了向量再改就是重算全库 |
| 中文全文检索 | **要定扩展**（pgvector 只管语义，不管关键词） | 小 |
| 异步任务 worker | 要加（表已经有了） | 中 |
| **模型推理位置** | **必须在校内**（数据不出校） | 大，见 §0 |

## 1. 已定约束（2026-10-20 学院确认）

> **数据可以出校，使用国内大模型 API；校外可以访问网站。**

这条把方案从"必须自建推理"改回"调用 API"，一期**不需要显卡**。但约束不是消失了，而是换了个方向：

| 原来防什么 | 现在防什么 |
| --- | --- |
| 数据被发到校外 | 数据被发到**没批准的供应商** |
| 误调外部 API | 接到来路不明的代理/中转站（很多"便宜 API"其实是转发，能看到全部内容） |
| — | 用了哪个模型、花了多少、发了什么，事后说不清 |

### 1.1 允许清单，不是"外网全通"

代码在 `server/app/llm.py`，判断依据是 **base_url 的主机名**，不是 provider 名字——名字可以随便写，域名才是数据实际去的地方。

```
校内地址（私网 IP / localhost / *.edu.cn）  → 放行
已批准供应商（DeepSeek / Kimi / 百炼 / 智谱）→ 放行
其他外部地址                                → 拒绝，并提示怎么加白名单
地址无效                                    → 拒绝（不知道发去哪就不发）
```

三种模式由 `MODEL_EGRESS` 控制：

| 模式 | 用途 |
| --- | --- |
| `allowlist`（默认） | 生产。只有批准的供应商能收到内容 |
| `any` | 开发临时试新供应商，生产禁止 |
| `internal-only` | 若将来又要求数据不出校，一个环境变量切回去 |

有个细节值得说：**`internal-only` 模式的判断必须排在 `approved` 之前**。第一版写反了，导致切换到"数据不出校"时已批准供应商反而被放行——模式的全部意义就是禁止外部调用，这个顺序错了等于没切。已修，并有测试守着。

测试见 `server/tests/test_policy.py`，41 项，包括域名伪造（`api.deepseek.com.attacker.com` 必须被拒绝）。

### 1.2 账本：谁批准了这家供应商

数据库表 `model_endpoint` 记着：端点、模型、`data_scope`（internal/external）、embedding 维度、**批准人**。

半年后审计会问："为什么教材内容会出现在这家公司的服务器上？"——`v_external_endpoint_audit` 就是回答这个问题的。

### 1.3 出校之后仍然要守的边界

数据能出校≠什么都能发。三条建议保持：

1. **学生身份信息不进提示词**。教材片段、题干可以发；姓名、学号、成绩不要发。
2. **教材版权另说**。数据可以出校，不等于有权把受版权保护的教材内容传给第三方做训练。采购或授权问题仍要确认（见待决事项清单 D）。
3. **记住出口**。`textbook_chunk.embedding_model` 记录每条向量是谁生成的，换模型时新旧不能混用。

### 1.4 校外访问的安全边界

| 风险 | 处理 |
| --- | --- |
| 教材被批量抓取 | **不提供 PDF 直链与全文导出**，只返回回答所需的片段与页码 |
| API 费用被刷爆 | 按 IP + 账号双维度限流；单用户并发 1–2；`model_call` 记 token 用量 |
| 爬虫、恶意注册 | 登录后才可用（认证未接入前用邀请码/临时账号） |
| 数据被拖库 | 数据库不对外，只开 443；反代到内网 `127.0.0.1:8000` |

## 2. 已解决的：那个会清空数据的文件

之前 `db/schema.sql` 开头是 `DROP SCHEMA public CASCADE`——本地无所谓，**服务器上误执行一次，全部数据没了**。

现在已经改成迁移制：

```
db/migrations/0001_init.sql        基线（原 schema.sql 拆出）
db/migrations/0002_learning_jobs.sql  学伴/管线/评测表
db/migrate.py                      应用迁移，记录版本与校验和
db/schema.sql                      由迁移自动生成，**非破坏性**，只建不删
db/reset.dev.sql                   清库，文件名自带警告，生产禁用
```

三条纪律：

1. **不再手改 `schema.sql`**。改 `migrations/NNNN_*.sql`，然后 `--concat` 重新生成。
2. **已应用的迁移文件不许改**。`migrate.py` 会算校验和，改了就报错——迁移一旦上过生产就是历史，要改就新加一个文件。
3. **每次迁移自己包 `BEGIN/COMMIT`**，脚本会剥掉外层统一管理事务，避免"文件里的 COMMIT 提前提交一半"。

## 3. 现在必须定的两件事

### 3.1 embedding 模型与维度

表里写的是 `vector(1024)`。**PG 的向量维度是列类型的一部分，改维度 = 重建整列 = 全部向量重算。**

先澄清一个常见误解：**生成模型不产出向量。** DeepSeek（`deepseek-flash` / `deepseek-v4-pro`）与 Kimi（Chat / Responses / Messages）都只提供对话接口，**没有 embeddings 端点**。所以"用 DeepSeek 做向量化"不成立——生成和向量是两套模型，可以不同厂商，行业里通常也不同。

国内可用的文本向量模型（2026-10 核实，阿里云百炼）：

| 模型 | 维度范围 | 默认 | 单条 token 上限 |
| --- | --- | --- | --- |
| `qwen3.7-text-embedding` | 256~2560 | **1024** | 131,072 |
| `qwen3.7-text-embedding-flash` | 256~1024 | **1024** | 131,072 |
| `text-embedding-v4` | 64~2048 | **1024** | 8,192 |
| `text-embedding-v3` | 512~1024 | **1024** | 8,192 |
| `qwen3-vl-embedding`（多模态） | 256~2560 | 2560 | 32,000 |

关键机制：**维度是请求参数，不是模型固定属性**（MRL，可变维度）。同一模型可以要 1024 也可以要 2048。但一旦定下，全库必须统一。

**建议：锁 1024，一期直接用 `qwen3.7-text-embedding`（走百炼 API）。** 三条依据：

1. **厂商自己就推荐 1024 作通用默认**。百炼文档原文：存储有限选 256/512，通用场景选 1024（默认值），精度要求高才上 1536/2048。
2. **1024 是候选模型的交集**。BGE-M3 原生 1024；qwen 全系可设 1024；`v3` 上限就是 1024。锁 1024，将来在云端 qwen 与本地 BGE-M3 之间切换，**表结构一行都不用改**。
3. **数学场景的瓶颈不在维度**，在切片质量与混合检索。2560 维救不了"公式被切成两半"。

既然数据可以出校，就不必为了向量化自建 GPU 服务：**embedding 走 API 是最省事的**，一次性把教材跑完即可。BGE-M3 作为"以后要数据不出校"时的替代方案保留，1024 维不变。

`textbook_chunk` 有 `embedding_model` 列。换模型时**新旧向量不能混用**——混在一起检索不会报错，只会悄悄变差，这是最难查的那类问题。

### 3.1b 多语言教材：1024 够不够

够，但**能不能跨语言检索不取决于维度，取决于模型**。

- **BGE-M3 本身是多语言模型**（100+ 语言），并且支持跨语言检索：中文提问可以命中英文段落，共用同一个向量空间。
- **qwen 系列同样多语**，且维度可设 1024，与 BGE-M3 对齐。

维度在多语言场景里唯一的实际影响是"预算被摊薄"：同一个 1024 维空间要同时容纳多种语言的术语，碰撞概率上升。实践中的量级是：**中英双语用 1024 完全够；到五种以上语言、且要互相检索时，可考虑 1536/2048，但收益远小于"换更好的多语言模型"**。

真正会卡住你的不是维度，是这三件事（已在 `db/migrations/0003_multilingual.sql` 补上）：

| 问题 | 表现 | 解法 |
| --- | --- | --- |
| **分词配置选错** | 英文教材用中文二元组切，命中率低 | `textbook.language` 决定全文检索用哪套配置：`zh`→pg_bigm，`en`→PG 内置 `english` 词典 |
| **术语对不上** | 学生用"一致收敛"问，教材写 uniform convergence | `glossary_term` 中英对照表，查询时先做术语扩展 |
| **混排段落误判** | 英文教材里夹一段中文批注 | `textbook_chunk.language` 可单独覆盖，`v_chunk_language` 统一取实际语言 |

术语表必须人工维护。**不要指望通用翻译**：`uniform convergence` 机器会译成"均匀收敛"，而数学界固定译法是"一致收敛"。这种错不会有任何报错，只会让学生觉得"这 AI 不懂数学"。

### 3.2 中文检索：向量不够，必须混合

纯向量检索在数学场景有个硬伤：**符号和专名检索不准**。"Cauchy 收敛准则"、"Lipschitz 条件"、"Riemann 可积"这类词，向量会召回一堆语义相近但术语不对的段落；而学生问的往往就是术语。

所以需要**混合检索 = 向量 + 关键词**。关键词这一路，PostgreSQL 的三个选择：

| 方案 | 安装 | 中文效果 |
| --- | --- | --- |
| `pg_bigm` | 简单（apt 有包） | 无需分词词典，二元组匹配，对术语友好 |
| `zhparser` | 需 SCWS 词典 | 分词质量好，但数学术语需自定义词典 |
| `pg_trgm` | 自带 | 适合模糊匹配，不适合语义 |

**建议 `pg_bigm` 管中文，PG 内置 `english` 配置管英文**，按 `textbook.language` 分支选择。英文不需要 `pg_bigm`——PG 自带的 english 词典能做词干还原（converge / converges / convergence 视为同源），这个中文反而用不上。

英文教材还有一个隐性优势：**数学符号与公式是跨语言共享的**。`$\lim_{n\to\infty} a_n = A$` 在中英文教材里写法一致，所以数学的跨语言检索比一般文本容易得多。

## 4. 服务器规格

数据可以出校、模型走 API，所以**一期不需要任何显卡**。

| 项目 | 建议 | 说明 |
| --- | --- | --- |
| CPU | 4–8 vCPU | 切片/OCR 吃 CPU；纯 API 2 核也够 |
| 内存 | 16 GB | PostgreSQL 给 4–8 GB，其余给应用与 worker |
| 磁盘 | 200 GB SSD | 教材 PDF 是主要占用（扫描件一本 100–300 MB） |
| 系统 | Ubuntu 22.04 / 24.04 LTS | 长期支持，Docker 与 PG 官方源齐全 |
| 数据库 | PostgreSQL 16 + pgvector 0.7+ + pg_bigm | 用 `pgvector/pgvector:pg16` 镜像最省事 |
| 运行时 | Python 3.12 | 与本地开发一致 |
| 网络 | 只开 80/443，数据库不对外；**出站需放通模型 API 域名** | 5432 只监听 127.0.0.1 |
| 显卡 | 无 | 一期全部走 API |

一个容易漏的运维点：学校的服务器通常**出站默认收紧**，要单独放通 `api.deepseek.com`、`dashscope.aliyuncs.com` 等域名，否则部署完出现"代码没问题但一直超时"。

向量占用估算：10 万切片 × 1024 维 × 4 字节 ≈ 400 MB，HNSW 索引约再乘 1.5。这个量级单机完全够。

### 4.1 什么时候才需要自建推理

只有三种情况需要回头买卡：

1. 供应商涨价或接口变更，成本不可控
2. 出现必须"数据不出校"的新要求
3. 需要微调（比如按学院教材风格训练批改模型）

真到那天，估算参考：

| 模型规模 | fp16 显存 | int4 量化 | 单卡可行 |
| --- | --- | --- | --- |
| 7B–8B | ~16 GB | ~6 GB | 24 GB 单卡，5–10 并发 |
| 14B | ~28 GB | ~9 GB | 24 GB 单卡只能跑 int4 |
| 32B | ~64 GB | ~20 GB | 需 48–80 GB |
| 70B+ | ~140 GB | ~40 GB | 多卡，不如用校内网关 |

代码已经为此留好了开关：`MODEL_EGRESS=internal-only` + 改 `LLM_BASE_URL` 指向内网，一处配置切回"数据不出校"，不用改业务代码。
## 5. 部署拓扑

```
                 ┌─────────────────────────────┐
  学生/教师 ──443─▶│ nginx（TLS、静态站、限流）   │
                 └──────────┬──────────────────┘
                            │ 127.0.0.1:8000
                 ┌──────────▼──────────┐        ┌──────────────┐
                 │ FastAPI (uvicorn)   │───────▶│ PostgreSQL 16│
                 │  /api/v1/*          │        │ + pgvector   │
                 └──────────┬──────────┘        │ + pg_bigm    │
                            │ 入队               └──────────────┘
                 ┌──────────▼──────────┐
                 │ worker（pipeline_job）│──────▶ 教材 PDF / 图片
                 │  切片 / OCR / 向量化  │        （本地盘或 MinIO）
                 └─────────────────────┘
```

三件事必须分开进程：**API 不能跑切线任务**。一本教材切片+向量化是分钟级，塞进 HTTP 请求必然超时；超时后改成同步脚本，就再也没有进度、重试和失败原因。`pipeline_job` 表就是为此准备的。

## 6. 环境变量清单

DATABASE_URL=postgresql://whu:***@127.0.0.1:5432/whu_teaching
DB_POOL_MAX=8

LLM_MODEL=deepseek-flash
MODEL_API_KEY=                                   # 只放服务端，永不进前端

# 向量模型（阿里百炼）

EMBEDDING_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1

生成和向量来自两个厂商（DeepSeek + 百炼），所以密钥分开配：`LLM_API_KEY` 与 `EMBEDDING_API_KEY`。只配 `MODEL_API_KEY` 时两者共用，方便开发期只测一条链路。

## 7. 从本地到服务器的步骤

```bash
# 1. 装依赖
apt install postgresql-16 postgresql-16-pgvector postgresql-16-pg-bigm nginx docker.io

# 2. 建库（注意 locale：影响中文排序）
sudo -u postgres createdb -E UTF8 --locale=zh-x-icu whu_teaching

# 3. 建表（非破坏性，可重复执行）
DATABASE_URL=... python db/migrate.py --apply
DATABASE_URL=... python db/migrate.py --status      # 核对

# 4. 灌现有 14 门课
python db/build_seed.py
psql "$DATABASE_URL" -f db/seed.sql
psql "$DATABASE_URL" -c "SELECT count(*) FROM exercise;"   # 期望 4807

# 5. 起 API
cd server && pip install -r requirements.txt
uvicorn app.main:app --host 127.0.0.1 --port 8000 --workers 2

# 6. nginx 反代 + TLS
#    client_max_body_size 300m;   ← 教材上传必须放行大文件

# 7. 备份（每天）
pg_dump -Fc "$DATABASE_URL" > /srv/backup/$(date +%F).dump
```

第 2 步的 `locale=zh-x-icu` 容易被忽略：用默认 `C` 排序时，中文按字节序排，"张"会排在"李"前面，教师端列表会看着像乱序。

## 8. 问答与 AI 学伴的技术链路

这是"服务于以后"的核心，现在定的框架要能承接：

### 8.1 一次问答的完整路径

```
学生提问
  → 意图判断（概念解释 / 解题 / 作业求助 / 闲聊）
  → 混合检索：向量(pgvector) + 关键词(pg_bigm)，限本课程
  → 取 node_chunk 锚点 → 定位到 knowledge_node 与教材页
  → 组装上下文（教材原文 + 知识点正文 + 关联例题）
  → 生成（要求：每个结论必须给引用；没检索到就拒答）
  → 落库 ai_conversation / ai_message / ai_citation / model_call
  → 流式返回（SSE）
```

四个设计决定，现在框架里已经留好位置：

| 决定 | 位置 | 为什么 |
| --- | --- | --- |
| **没有引用就拒答** | `ai_message.refused` | 数学答案错了比不答更糟；学生无法判断对错 |
| **引用指向具体切片** | `ai_citation.chunk_id → textbook_chunk` | 才能回答"第 78 页第 2 段"，而不是"书上说过" |
| **每次调用记成本** | `model_call.cost_usd` | 不记就答不出"这东西一个月花多少钱" |
| **提示词版本化** | `model_call.prompt_version` | 换提示词后效果变差，没有版本号就无法归因 |

### 8.2 学伴的"因材施教"靠什么

不是靠提示词里写"请根据学生水平回答"——那是猜。靠的是数据：

```
exercise_attempt（每次作答，含用时、AI 初评、教师评分）
        ↓ 定期重算
node_mastery（每个学生对每个知识点的掌握度）
        ↓ 组进上下文
"该生在'一致收敛'上 3 次作答错 2 次，最近一次错在前提条件"
```

`exercise_attempt` 与 `node_mastery` 已在 0002 迁移里建好。关键取舍：**`node_mastery` 是缓存不是事实**——它能从 `exercise_attempt` 重算，所以模型改了、算法改了，丢掉重建即可，不会丢数据。

### 8.3 必须现在建的东西：评测集

`qa_eval_case / qa_eval_run / qa_eval_result` 三张表。

**没有评测集，就无法回答"换了模型之后是变好还是变差"。** 这件事只能在上线初期积累：先收 50 个真实问题（学生真会问什么），标注期望要点与是否必须引用，之后每次改提示词、换模型、重切切片都跑一遍。

错过这个窗口，后面补的评测集都是"工程师想出来的问题"，不是学生真问题。

## 9. 数据安全与合规

| 项 | 处理 |
| --- | --- |
| 教材 PDF | 版权材料，放 `textbooks/`（已 gitignore），不入库不进 git |
| 学生身份 | `user_ref` 可存学号哈希；`student_profile.consented_at` 为空则不得保存对话记忆 |
| 对话记录 | 设保留期（`retention_until`），到期清理；支持学生申请删除 |
| 模型调用 | 不外发题干以外的个人信息；调用日志保留 90 天 |
| 审核留痕 | `audit_log` 只追加不修改 |

## 11. 一句话总结

架构上**不用返工**：表结构、API、迁移机制、任务表、学伴数据表都已经按"单机 → 服务器"的路径设计。

上服务器前只需要做三件事：**定 embedding 模型（建议 BGE-M3 / 1024）、装 pg_bigm 做中文关键词检索、接学校统一身份认证**。前两件是技术选择，第三件要跟学校信息中心对接，**这个应该现在就开始问，因为流程比代码慢**。


## 从零建库：服务器上第一次部署的完整命令

这一段是给"代码已经传上去、库里还是空的"那种服务器写的。按顺序粘贴即可，每条都说明为什么。

### 1. 建角色与库

```bash
sudo -u postgres psql <<'SQL'
CREATE ROLE whu LOGIN PASSWORD '换成你的口令';
CREATE DATABASE whu_teaching OWNER whu ENCODING 'UTF8' TEMPLATE template0;
SQL

# 中文排序：默认 C 排序会把"张"排在"李"前面，教师端列表看着像乱序
sudo -u postgres psql -d whu_teaching -c "ALTER DATABASE whu_teaching SET lc_collate = 'zh-x-icu';"
```

`TEMPLATE template0` 不是可省项：模板库 `template1` 带上别的 locale 时，`lc_collate`
会建不进新库，报错发生在 `CREATE DATABASE` 那一步。

### 2. 建扩展（要用超级用户，且必须在迁移之前）

```bash
sudo -u postgres psql -d whu_teaching <<'SQL'
CREATE EXTENSION IF NOT EXISTS vector;      -- pgvector，向量检索的列类型
CREATE EXTENSION IF NOT EXISTS pgcrypto;    -- 迁移 0001 里也会建，先建省一次权限问题
SQL
```

`CREATE EXTENSION` 只有超级用户能做，普通角色 `whu` 会报
`permission denied to create extension`。先由 postgres 建好，后面迁移里的
`CREATE EXTENSION IF NOT EXISTS` 就成了空操作。

### 3. 建表（迁移制，可重复执行）

```bash
export DATABASE_URL='postgresql://whu:口令@127.0.0.1:5432/whu_teaching'
python db/migrate.py --apply          # 逐条应用 0001…0017，每条记版本与校验和
python db/migrate.py --status         # 全部「已应用」，没有「文件被改动」
```

**服务器上不要加 `--pglite-compat`。** 那个开关是给本机 PGlite（WASM PG，没有 pgvector）
用的，加了会把 `embedding` 降级成 `jsonb`，向量检索就废了，事后再改要重建整列。

### 4. 灌 14 门课的课程数据

```bash
python scripts/import_seed.py db/seed.sql
# 期望：课程 14、习题 4807、知识点 4485
```

整个脚本在一个事务里执行，失败整体回滚——导了一半的库比没导更危险。
不要用 `psql -f`：那个边执行边提交，中间出错会留下半截数据。

### 5. 建第一个管理员

```bash
python scripts/create_admin.py --username admin
# 交互式输两遍口令（至少 12 位、含数字、不含登录名）
# 自动标记 must_change_password：第一次登录必须改，不依赖前端自觉
```

不要在生产库跑 `scripts/dev_seed_accounts.py`——它塞的是文档里的默认口令，等于公开后门。
这个脚本现在检测到 `APP_ENV=prod` 会直接拒绝，并指向 `create_admin.py`。

### 6. 生成问答语料

```bash
python scripts/rebuild_qa_corpus.py
# 14 门课、约 4590 块，十几秒
```

seed 只带知识点正文，不带问答切片——`textbook_chunk` 是空的（教材 PDF 还没切）。
不跑这一步，AI 问答会一直说"暂时没有知识片段"。这一步和
`POST /api/v1/admin/qa-corpus/rebuild` 走同一个函数，不需要先登录拿 token。

### 7. 配环境变量并起服务

```bash
cp deploy/env.example /srv/whu/.env    # 仓库里带了模板，逐项改成你的
chmod 600 /srv/whu/.env
```

**一个容易踩的坑：`APP_ENV=prod` 时 FastAPI 不再托管前端。** `server/app/main.py`
的 `_mount_dev_static()` 只在非 prod 下执行，只挂 `secrets/`、`db/`、`server/` 之外的
白名单目录；prod 下它直接跳过——这样后端就不会把源码和密钥目录暴露在 HTTP 上。
代价是 **nginx 必须自己托管 `index.html` 与静态资源**，否则打开首页是 404，
而 API 一切正常，很容易误判成"前端丢了"。

单元文件与 nginx 配置都放在仓库 `deploy/` 里，直接复制：

```bash
sudo cp deploy/whu-teaching.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now whu-teaching

sudo cp deploy/nginx.conf.example /etc/nginx/sites-available/whu-teaching
sudo ln -sf /etc/nginx/sites-available/whu-teaching /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx
```

nginx 里三行不能少：

| 配置 | 少了会怎样 |
| --- | --- |
| `client_max_body_size 300m;` | 教材 PDF 上传直接 413（默认 1 MB） |
| `proxy_set_header X-Forwarded-Proto $scheme;` | 后端以为在 http 上，Secure cookie 不下发，登录"成功但立刻掉线" |
| `location ~ ^/(secrets\|db\|server\|scripts\|\.env\|\.tmp\|uploads)/ { deny all; }` | 密钥、seed 脚本、后端源码、原始 PDF 全部可被下载 |

### 8. 自检，再放开访问

```bash
python scripts/preflight.py
```

退出码 0 = 可以上线；1 = 有阻断项。它查的正是上面这些容易漏的：迁移是否全应用、
扩展在不在、`CORS_ORIGINS` 是否还是 `*`、生产是否还开着演示模式、端点是否缺密钥。

### 9. 备份与恢复演练

```bash
pg_dump -Fc "$DATABASE_URL" > /srv/backup/$(date +%F).dump
# 每月至少恢复一次到临时库，否则不算备份（见 docs/回滚与恢复.md）
```

## 上线自检（`scripts/preflight.py`）

部署完成后，先跑这一条，再决定要不要放开访问：

```bash
python scripts/preflight.py                       # 读 DATABASE_URL 等环境变量
python scripts/preflight.py --url postgresql://…  # 显式指定库
python scripts/preflight.py --offline             # 不连库，只查配置与依赖
```

退出码 0 = 可以上线（允许有警告）；1 = 有阻断项。

它检查的东西，以及**为什么这些是阻断而不是警告**：

| 项 | 阻断条件 | 理由 |
| --- | --- | --- |
| 身份认证组合 | `APP_ENV=prod` 且 `AUTH_MODE=dev` | 任何人带 `X-Actor` 头就能冒充管理员 |
| 演示模式 | 生产开 `DEV_FAKE_MODEL=1` | 学伴会返回固定的演示文本，学生看到的是假答案 |
| 出校策略 | `MODEL_EGRESS` 取值非法 | 非法值时行为退化为"允许一切"，而人以为限制还在 |
| 数据库 | 连不上 / 无 `schema_migration` / 有未应用迁移 | 后端启动即失败 |
| 迁移校验和 | 已应用迁移的文件被改过 | 库与代码不一致，后续迁移会错位 |
| pgvector | 扩展未安装 | 教材切片检索不可用 |
| 模型端点 | 启用的端点缺密钥文件 | 问答与向量化会失败，且报错发生在课堂上 |
| 密钥目录 | 非 Windows 上权限位过宽 | 密钥对其他用户可读 |

三项**标为"无法检查"而不是"通过"**：证书与反向代理、备份可恢复性、供应商侧的行为。
理由很简单——脚本没有能力证明这些，写成"通过"就是骗人。备份尤其如此：
没演练过恢复的备份不算备份。

自检脚本自己也有测试（`npm run test:preflight`，14 项）：正面验证危险配置会被阻断、
连不上库不会被静默跳过、缺 pgvector 会被指出。测试时会起一个真的 PostgreSQL（PGlite）
跑完整检查，而不是用假数据拼输出。


## 导入课程数据（scripts/import_seed.py）

db/seed.sql 是 12 MB、14935 条 INSERT 的整库脚本，在一个事务里执行：

```bash
python scripts/import_seed.py db/seed.sql          # 取 DATABASE_URL
python scripts/import_seed.py db/seed.sql --truncate   # 仅测试库：先清空业务表
```

失败整体回滚。这一点重要：导了一半的库看起来是好的，比没导更危险。

导入后逐表打印行数。服务器上的期望值是：课程 14、习题 4807、知识点 4485。

**这条路径有测试了。** `npm run test:seed` 会起一个真的 PostgreSQL（PGlite），应用迁移、导入 db/seed.sql、再核对 16 项：

- 结构：行数、孤儿挂载、题目是否都挂在存在的章下、枚举取值是否只有那四种；
- 内容质量：书页覆盖率 3537/4807、PDF 页 3851/4807、题号 4582/4807；
- 质量守恒：判成自拟的题出处里必须真的写了自拟，判成导出表的必须真的提到导出，
  带待核的题必须停在 draft。

在此之前这份 12 MB 脚本**从未被执行过一次**——`npm run verify:db` 只是解析文本。
静态检查看不出语法错误、约束冲突、枚举写错，而这些恰好会在服务器上第一次导入时炸。
