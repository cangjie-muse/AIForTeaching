# 审核分层与「学生可见范围」

## 一、分层在哪里：不是新概念，库里早就有

审核分级的数据结构在 `db/schema.sql` 里，不需要新建：

| 层 | 数据来源 | 现在由谁产生 |
| --- | --- | --- |
| **未审核** `none` | 没有 `human_verified_at`，也没有通过校验的 Lean 证明 | 导入 / AI 生成后默认状态 |
| **Lean 形式化验证** `lean` | `lean_proof` 有 `compiled = true` 且 `faithful_status = 'teacher-reviewed'` | **还没有产线**（表与判定已就位，见下文） |
| **人工审核** `human` | `exercise.human_verified_at` 非空 | 审核页点「发布」即写入 |
| **两者都有** `strongest` | 上面两条同时成立 | 同上 |

合成视图是 `v_exercise_verification.tier`（`none / lean / human / strongest`）。
另有一个 `v_publishable_exercise`：只有 `human`、`strongest` 的题才算"可进正式作业与考试"。

页面上能看到它们的地方：

- **内容审核页**（`#/review`）顶部大盘按 `tier` 统计；
- 队列每一行有徽标：未核 / Lean 校验 / 人工通过 / 双重通过；
- 审核详情里勾「人工审核通过」写 `human_verified_at`。

## 二、缺的是"口径"，不是"分层"

原来学生端只看两件事：课程发布 + 题目 `review_status = 'published'`。
这等于**默认所有已发布的题都发**——即使没人看过内容，只要点了发布就上线。

现在加了第三道闸 `visibility_policy`（迁移 `0011`）：

```
学生能看到什么 = 课程已发布 AND 题目已发布 AND 题目等级在允许范围内
```

三档（从严到宽）：

| 档位 | 允许的等级 | 学生端能拿到 |
| --- | --- | --- |
| `human` 仅人工审核通过 | `human`、`strongest` | 只放老师逐题确认过的题 |
| `verified` Lean 验证 + 人工审核 | `lean`、`human`、`strongest` | 加上形式化验证过的题 |
| `all` 全部（含未验证） | 四个全放 | 与引入本表之前完全一致 |

**默认 `all`**：升级不会让学生端突然空掉。三档是包含关系（`human ⊂ verified ⊂ all`），
这条不变式有测试钉住——写错一个等级名，学生端会静默少题或多题。

## 三、开关在哪、怎么用

内容审核页顶部新增「学生可见范围」面板：

- 两个下拉：**习题与测验**、**AI 问答（完整解答）**，可以分别设；
- 每个选项后面直接写「学生可见 N 题」——**保存前就能看到后果**；
- 某一档会清空学生端时，面板给出橙色警告，并指出两条出路（先去审核 / 换回更宽的档）；
- 保存后立即生效，写 `audit_log`（`visibility.update`）。

只有 `teacher / reviewer / admin` 能改；学生调用 `PUT /api/v1/visibility` 是 403。

## 四、生效范围

1. **公开目录** `GET /api/v1/catalog`、`GET /api/v1/catalog/{id}`
   题量统计与题目列表都按档位过滤。知识点不受影响——知识点没有"验证等级"这一维，
   正文由老师在「课程内容」页直接改，改完即定稿；这条分工没变。
2. **AI 问答的完整解答模式**（`mode=full`）
   两道条件独立：先要学生有作答记录（作答解锁），再要题目等级在允许范围内（信任解锁）。
   不满足时返回 403 并说明"这道题当前等级不在学生可见范围内，可以先用引导模式"。
   引导模式（`mode=guide`）不受影响——不给完整解答，也就没有"放出未审核内容"的问题。

## 五、Lean 那一层现在是什么状态（说清楚）

- 表 `lean_proof` 与视图里的 `lean` 判定**已经存在**：编译通过 + 形式化忠实性人工确认；
- 但**还没有 Lean 编译器接入**：没有产线去生成 `statement_lean`、跑 `lake build`、回填
  `compiled`。所以真实数据里 `lean` 与 `strongest` 目前都是 0 题；
- 因此选「Lean 验证 + 人工审核」这一档，**效果与「仅人工审核」相同**（现在没有 Lean 题）。
  这是数据现状，不是 bug。

要真做这一层，需要：Lean 4 + mathlib 的构建机（一次性装、按题构建，慢且吃内存）、
每道题的形式化脚本、以及"形式化是否忠实于原题"的人工确认流程。这是一期之后的事，
当前把开关和判定先摆好，接上验证器即可生效。

## 六、测试

- `server/tests/test_visibility.py`（18 项）：三档包含关系、未知档位 400、默认值、
  SQL 片段与参数。
- `server/tests/e2e_api.py`（+13 项，真实 PGlite）：默认 `all`、非法档位 400、
  切到 `human` 后未人工确认的题从目录与统计里消失、知识点不受影响、学生不能改、
  切回 `all` 恢复。
- `scripts/test-view-visibility.cjs`（22 项）：面板文案、两个下拉、每档可见题量、

- `npm run check`（253 项）、`npm run test:view`（334 项）、`npm run test:api`（205 项）全绿。

## 七、还没做

- **Lean 验证没有产线**（见第五节）。分档已就位，`lean` 档现在等价于 `human`。
- **`review_status` 与 `tier` 是两套状态**：一处说"工作流走到哪"，一处说"可信到什么程度"。
  页面上同时显示两者，但还没做一个"这两个状态不一致"的巡检（例如已发布却 `tier=none` 的题）。
  这次端到端测试就是手工造了这种数据来验证闸门有效——生产上应该有个定时报表。
- **按课程设置**：现在是全平台一个口径（接口留了 `course_id` 只用于统计）。
  如果出现"数学分析严格、试点课全放"的需求，需要把表改成 `(course_id, tier)` 复合键。
- **问答的教材片段没有等级**：`textbook_chunk` 没有 review_status，所以问答的检索层
  暂时无法按"教材审到哪一页"过滤；现在只按版权状态过滤（`internal-only` 不外传）。
