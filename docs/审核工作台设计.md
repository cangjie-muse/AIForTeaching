# 审核工作台设计

日期：2026-10-20。面向：学院教学管理、题库建设。
本文回答：**为什么需要审核界面、三档标签怎么建模、界面长什么样、什么条件下才允许发布。**

## 1. 两个维度，不是一个下拉框

你描述的三个层次（网上搜集 → Lean 验证 → 人工审核）容易被做成一个下拉框，但它们在语义上是**两件不同的事**：

| 维度 | 回答的问题 | 取值 |
| --- | --- | --- |
| **工作流状态** `review_status` | 这条内容走到哪一步了 | draft / machine-checked / teacher-reviewed / published / retired |
| **可信等级** `tier` | 这条内容凭什么可信 | none / lean / human / strongest |

为什么要分开：一道题可能**人工审核过但没有形式化**（绝大多数），也可能**Lean 验证过但没人读过题干是否适合教学**（形式化只管命题真假，不管教学适用性）。合成一个字段后，"退回修改"会连带丢掉"已经 Lean 验证"这个事实——这是信息损失，而且不可恢复。

## 2. 三档标签的落地

```sql
exercise.human_verified_at / human_verified_by   -- 人工审核证据
exercise.lean_verified_at                        -- 有 Lean 证明（冗余，便于筛选）
lean_proof(compiled, faithful_status, ...)       -- Lean 证据链明细
```

由 `v_exercise_verification` 视图合成四档：

| tier | 含义 | 学生可见 | 可进正式作业 |
| --- | --- | --- | --- |
| `strongest` | 人工审核 **且** Lean 证明（两证齐全） | 是 | 是 |
| `human` | 仅人工审核 | 是 | 是 |
| `lean` | 仅 Lean 证明 | 仅教师端 | **否**（见下） |
| `none` | 都没有（网上搜集的默认落这里） | 否 | 否 |

**为什么 `lean` 不算"可发布"**：Lean 证明的是"你写下的那个命题"。命题写对不等于题出得好——条件是否完整、结论是否恰当、是否适合该年级，形式化一概不管。所以 `lean` 只作为**教师端参考**，不进正式作业。

### 当前存量（实跑数据）

| tier | 题数 |
| --- | --- |
| none | 4807 |
| lean | 0 |
| human | 0 |
| strongest | 0 |

也就是说，**现在一道可发布的题都没有**。这是对的：现有 14 门课的数据全部通过了机器校验（公式可渲染、外键完整），但没有一道经过人工确认。`v_publishable_exercise` 返回 0 行——发布闸门是有效的，不是摆设。

## 3. Lean 证据链：六件事必须成对记录

```sql
CREATE TABLE lean_proof (
  statement_lean,       -- 形式化后的命题（Lean 源码）
  proof_file, proof_sha256,   -- 证明文件与哈希
  toolchain,            -- leanprover/lean4:vX.Y.Z + mathlib@<commit>
  build_log_sha256,     -- 编译日志哈希，防"口头验证"
  compiled, compiled_at,-- 是否编译通过
  faithful_status,      -- 形式化是否忠实于原题（独立人工确认）
  faithful_by, faithful_note
);
```

**核心矛盾**：`compiled = true` 只证明"形式化命题成立"。如果形式化时漏了条件（把连续的 $f$ 写成任意 $f$），证明再漂亮也救不回原题。

所以 `faithful_status` 是**独立的一列**，且必须是 `teacher-reviewed` 才允许 Lean 计入可信等级。

**这个约束在实现时被写漏过，是测试抓出来的。** 我最初的 `v_exercise_verification` 里，`lean` 分支只判断了 `p.compiled`，没有判断 `faithful_status`——结果任何"编译通过但形式化没人看过"的题都被标成"Lean 已验证"。回归测试里加了反例：

```
✓ Lean 已编译但忠实性未确认 → tier 仍为 none
✓ 形式化经确认 → tier=lean
✓ Lean + 人工审核 → strongest
```

这三条现在固化在 `npm run verify:db`，谁改视图都会被拦住。

## 4. 状态机

```
        ┌──────────────────────────────────────────────┐
        │                                              │
   draft ──机器校验──> machine-checked ──入队──> pending
                                                  │
                     ┌────────────────────────────┼──────────────────────┐
                     ▼                            ▼                      ▼
            changes-requested                 approved               rejected
            （退回，附错误清单）            （教师确认，待发布）    （重复/版权不明）
                     │                            │
                     └──── 重新提交 ──────────────┴──> published（学生可见）
                                                          │
                                                     retired（被新版取代）
```

硬规则：

1. **`published` 的内容不得原地修改**。要改必须 `published → retired` 并建立新版本，否则学生正在做的题会无记录地变化。
2. **退回必须带错误清单**（`review_issue` 至少一条），不能只写"退回"。
3. **每次状态变更写 `audit_log`**，带操作者、时间、理由。

## 5. 错误分类（`review_category`）

分类不是为了好看，是为了**统计质量趋势**和**批量处理**。14 类：

| 组 | 分类 | 谁能判 |
| --- | --- | --- |
| 内容 | `content-error` `answer-error` `answer-missing` `format-error` | 教师 |
| 挂载 | `wrong-node` `missing-node` `over-linked` | 审核员 |
| 溯源 | `source-missing` `source-wrong` `page-imprecise` | 审核员 |
| 其他 | `difficulty-mismatch` `duplicate` `hierarchy-error` `other` | 教师 / 审核员 |

**挂载错误与内容错误必须分派给不同角色。** 审核员看题干就能判断"这题该挂在极限还是连续"，但判断不了"这个答案的收敛性讨论对不对"。混在一起会让审核员卡在不会的题上，队列就堵死了。

## 6. 界面四屏

### 6.1 队列

```
┌ 审核队列 ──────────────────────────────────────────────────────┐
│ 课程 [数学分析 I ▾] 错误类型 [全部 ▾] 等级 [未审核 ▾] 状态 [待审 ▾]│
│ 积压 412 · 今日已审 87 · 平均 34 秒/条 · Lean 已验 0            │
├────────────────────────────────────────────────────────────────┤
│ ☐ 全选  [批量通过] [批量改挂] [批量补页码] [批量标 Lean]         │
├────────────────────────────────────────────────────────────────┤
│ ☐ CJX-I-XLSX-r234  对实数 a₁…aₙ 和 b₁…bₙ 成立…                  │
│    tier: none  来源: 同事导出表  溯源: pageless                 │
│    ⚠ 2 条问题：wrong-node(次要) · page-imprecise(主要)          │
│ ☐ CJX3-U-2.1-E1    设 f 在 [a,b] 连续…                          │
│    tier: lean  来源: 教材原题 p.27 §2.1-1   ✓ 溯源完整          │
└────────────────────────────────────────────────────────────────┘
```

### 6.2 详情与编辑

左只读（KaTeX 渲染，看公式是否真的对）、右编辑。三个编辑区：

- **题干 / 答案**：改动后即时渲染，比较"改前改后"
- **知识点挂载**：双栏选择器（左课程树、右已挂），**改挂必须选原因**
- **溯源**：书名 + 书页 + PDF 页 + 原题号，四个字段分别填

### 6.3 修订对比

`exercise_revision` 存了每次更新前的完整快照（题干、答案、难度、挂载、页码、审核状态、操作者）。对比页显示 `v(n-1) → v(n)` 的差异，供教师复核审核员改了什么。

这次改动由 `BEFORE UPDATE` 触发器自动完成，**不依赖界面自觉**——任何 UPDATE 路径（API、批量脚本、手工 SQL）都会留痕。

### 6.4 争议与退回

`changes-requested` 回到导入人，附错误清单与截图。改完重新入队，保留历史轮次。

## 7. 批量操作：决定这件事能不能完成

**4807 道题逐条审是不可能完成的。** 按 34 秒/条，一个人不休息要 45 小时。所以必须有批量：

| 批量 | 场景 | 安全约束 |
| --- | --- | --- |
| 按来源批量确认 | 同事导出表的 702 道题，行号连续、同源 | 每条仍写独立 `audit_log`，共享 `batch_id` 可整体回滚 |
| 按知识点批量改挂 | 整个子树挂错到父节点 | 改挂前要求预览"将影响 N 道题" |
| 按规则批量补页码 | 某章所有题页码相同 | 只填空白，不覆盖已有值 |
| 批量标 Lean | 一次导入一批 Lean 证明文件 | 只写 `lean_proof`，`faithful_status` 仍须逐条确认 |

## 8. 发布闸门

```sql
CREATE VIEW v_publishable_exercise AS
  SELECT ... FROM exercise e
  JOIN v_exercise_verification v ON ...
  WHERE v.tier IN ('human', 'strongest')
    AND e.review_status = 'published'
    AND (e.provenance NOT IN ('web', 'ai-generated') OR e.license IS NOT NULL);
```

三道闸：**人工审核过 + 已发布 + （网上/AI 题必须有 license）**。

网上搜集的题默认 `provenance='web'`，数据库层面强制要求 `source_url`（`CHECK` 约束，本次已验证会被拒绝）：

```
✓ web 来源缺 source_url 被数据库拒绝
```

## 9. 权限

| 角色 | 能做 | 不能做 |
| --- | --- | --- |
| 审核员 reviewer | 认领、改题干/答案、改挂载、补溯源、提交 | 终审、发布 |
| 教师 teacher | 终审、判内容与答案正确性、标 Lean 忠实性 | 发布（由管理员） |
| 管理员 admin | 发布、批量回滚、管理账号 | — |
| 学生 | 只读已发布内容 | 一切写操作 |

**职责分离**：导入人与终审人最好不同。单人学院做不到时，至少**记录**导入人与审核人，让事后追溯成为可能——这也是 `audit_log` 存在的理由。

## 10. 验收指标

| 指标 | 目标 | 说明 |
| --- | --- | --- |
| 审核吞吐 | ≥ 60 条/人时（批量后） | 逐条是 105 条/人时，批量必须把吞吐拉高数倍 |
| 一次通过率 | 记录，不设目标 | 太低说明导入管线有问题 |
| 返修率 | < 20% | 退回后再审的比例 |
| 待核积压 | 逐周下降 | 当前 1096 条 draft + 809 条 unknown 溯源 |
| 挂载错误率 | < 5% | 抽检 200 道 |
| 可发布题数 | 从 0 增长 | 这是学院汇报最有说服力的数字 |

## 11. 首轮自动建队结果（实跑）

用 `POST /api/v1/review/queue/build` 的同一段 SQL 在 WASM Postgres 上跑了一遍，结果：

```
✓ 建队：未发布题目全部入队 — 4807 条
✓ 自动生成错误清单 — 3175 条 issue
    错误分类分布： page-imprecise=1270, content-error=1096, source-missing=809
✓ 队列查询返回结构化行 — 样本 3 行
✓ 发布后进入可组卷视图 — 可发布 1 道
✓ 发布动作也留下修订快照 — 1 版
```

三个数字值得注意：

1. **`missing-node` = 0**：4807 道题全部至少挂了一个知识点。挂载结构本身是干净的，问题在"挂得对不对"，而那个只有人能判——所以挂载错误不会出现在自动队列里，只能靠抽检和教师反馈。
2. **`page-imprecise` = 1270**：26% 的题没有精确书页。这是问答溯源最直接的缺口，也是 S1 教材切片的第一个要解决的问题。
3. **`content-error` = 1096**：全是原文自带"待核"标记的题。注意这是 `minor` 级——"待核"不等于"错了"，只是没人确认过。

还有一个设计上的修正：最初的队列只挑 `review_status = 'draft'`，漏掉了 3711 道 `machine-checked`。**机器校验通过 ≠ 人看过**，所以队列必须覆盖所有未发布内容（4807 条），靠 `priority` 排序分批处理，而不是靠状态过滤。

## 12. 实施顺序

| 步骤 | 内容 | 状态 |
| --- | --- | --- |
| 1 | 数据模型：`review_task` / `review_issue` / `exercise_revision` / `lean_proof` / 三档视图 | **已完成**（`db/migrations/0001_init.sql`，7 条约束测试 + 建队端到端测试通过） |
| 2 | 审核 API：队列查询、入队、决定、改题、改挂载 | 下一步 |
| 3 | 审核界面：队列 + 详情 + 对比 + 批量 | 依赖 2 |
| 4 | 只读审核看板（给学院看积压与进度，不写入） | 可与 2 并行 |

**审核界面不能做在前端 localStorage 里**：审核结论要多人可见、要留痕、要可回滚、要有真实身份。这四条 localStorage 一条都做不到。所以顺序必须是 数据结构 → API → 界面，反过来做会推翻重写。
