### 落卷链真的跑到了哪一步

`server/tests/test_assembly_pipeline.py` 用的是**真实服务**，只替换求解器与授权端口：

```
真实 BlueprintService          建约束组卷蓝图（assembly_mode=constraint_assisted）
真实 CandidateService          固定候选快照
真实 AssemblyCandidateService  翻译成带哈希的候选 manifest
真实 AssemblyService           启动运行 → 选方案
真实 PaperService              建草稿卷（写入 assembly_run_id + selected_solution_index）
真实 PaperValidationService    独立整卷校验（重读库、重算 manifest）
```

断言里有五条是"拒绝"：

- 预检已证无解时**不调求解器**（`solver.calls == 0`），运行记 `infeasible` 并附原因；
- `UnavailableSolver`（本机真实状态）让运行 `failed`、`solution_manifest` 为空、
  `select` 抛 `RunNotSolved`，且**一份卷子都没建**；
- 求解器声称有解却没给方案 → 抛错，不记成一次成功；
- 改掉方案里的一道题 → 重算哈希不一致 → `SolutionMismatch`，不建卷；
- 阶段 A 复验不通过 → 运行标 `FAILED`、卷子留在草稿、抛 `AssemblyValidationBlocked`。

## CP-SAT 求解器：服务器上的真实结果（2026-11-06）

本地开发机（Windows，无可用外网出口）装不上 ortools，所以以下结论**全部来自
`mathagent` 服务器**（Ubuntu 26.04 / Python 3.14.4 / ortools 9.15.6755 / PostgreSQL 18.6）。

```
$ .venv/bin/python server/tests/test_assembly_solver.py
✓ CP-SAT 求解器测试全部通过（13 项）

$ .venv/bin/python scripts/load_assembly.py --slots 50 --candidates 1000 --seconds 60
规模：1000 道候选 / 50 个槽位
  构造蓝图                2.1 ms
  构造候选              107.7 ms
  固定候选 manifest     227.1 ms
  计算每槽候选供给       42.6 ms
  求解前预检             44.8 ms
  候选清单（1000 道），每槽可选 500/1000，预检无问题
  求解：optimal（ortools 9.15.6755，14435 ms；变量 37500）
```

**这是单机单次运行的耗时，不是生产 SLO**：并发、真实候选分布、多方案
（`max_solutions>1`）都没有压测。

### 为什么钉 9.15 而不是计划书的 9.11

`ortools 9.11.4210` 只提供到 **cp312** 的 wheel（已核对 PyPI），而服务器只有
Python 3.14；`9.15.6755` 提供 cp314 manylinux 轮子，且本仓库只用 CP-SAT 稳定 API。
锁定值同步写在 `server/requirements-assembly.txt` 与
`test_assembly_candidate.py` 的版本断言里。

### 首跑暴露并修掉的四个真问题

| 现象 | 根因 | 修法 |
| --- | --- | --- |
| `add_forbidden_assignments() missing 1 positional argument` | 传了变量名字符串，API 要**变量对象 + 禁止取值元组** | `AddForbiddenAssignments(vars, [[1]*n])` |
| `SolverUnavailableError：未安装 ortools`（明明装了） | `default_solver()` 在 9.11 装不上时被写成"一律返回不可用" | 有 ortools 就返回 `CpSatSolver`，并加测试钉住 |
| 一条**写反的**断言（"两道候选必有一道没用上"） | 两槽两题必然是"两道都用上" | 改成断言"互不相同且恰好是这两道" |
| 60 秒零可行解（`timeout, time_limit_no_solution, 变量 37500`） | 时长上限与时长目标都写成一条 **37,500 项**的和式 | 按槽位聚合成 50 个辅助变量（数学恒等，约束一条没少） |
| `NameError: self` 在 `@staticmethod` 里 | 改造时把 `self._total_duration()` 写进了静态方法 | 改回普通方法；并加**源码级 AST 测试**禁止 staticmethod 里出现 `self` |

另外删掉了"总分 == 蓝图总分"这条冗余等式：每个槽位 `AddExactlyOne` + 槽位分是常量，
该等式与选择无关、恒成立；写在模型里只会让求解器处理一个 50,000 项的必然约束。
蓝图分数自洽由 `precheck`（`blueprint_score_mismatch`）负责。

### 超时与无解不再混为一谈

`_solve_all` 现在自己返回结论，`solve()` 按结论写 `diagnostics.reason`：
`time_limit_no_solution`（调大时限/缩小规模）与 `hard_constraints`（改蓝图）。
上一版把"时间不够"报成了"约束冲突"，教师会去改根本不需要改的地方。
### 已写好但**一次都没跑过**的求解器

`server/app/assembly/solver.py`（`CpSatSolver`）与 `server/tests/test_assembly_solver.py`
是 TDD 的"先写测试"产物，但缺依赖使它们停在"未验证"：

```
$ .venv\Scripts\python.exe server/tests/test_assembly_solver.py
⊘ 未验证：本机未安装 ortools，CP-SAT 求解器的断言一次都没有运行过。
  安装后重新运行：.venv/Scripts/python.exe -m pip install -r server/requirements-assembly.txt
```

它刻意**没有**登记进 `npm run check`：没装依赖时它只能打印"未验证"，而"跳过"在
批量输出里看起来和"通过"太像。装好依赖后要单独跑，并额外确认 `map_status` 不把
FEASIBLE/TIMEOUT 说成 OPTIMAL、备选方案不继承"已证明最优"。

## 固定卷阶段 B：方案复验与 A/B 配对入口（2026-11-06）

### 方案复验（不需要求解器的那一半门禁）

阶段 B 门禁要求「CP-SAT 硬约束与独立整卷校验结果一致」。其中"给一份方案，它满足
蓝图吗"只依赖方案与蓝图，纯函数可算——`server/app/assembly/verification.py`（17 项
测试）就是这一层：

| 检查 | 不通过时 |
| --- | --- |
| 每槽分值 = 蓝图、合计 = 蓝图总分 | `score_mismatch` / `total_score_mismatch` |
| 缺槽 / 重复槽 / 蓝图没有的槽 | `missing_slot` / `duplicate_slot_selection` / `unknown_slot` |
| 所选题在候选清单里 | `selected_unknown_candidate` / `selected_excluded_candidate` |
| 时长上限 | `duration_exceeded`；缺时长报 `duration_unknown`（不虚构 0 秒） |
| 覆盖与题型区间 | `coverage_shortfall` / `kind_below_minimum` / `kind_above_maximum` |
| 同题重复、蓝图互斥组、题内冲突组 | `duplicate_exercise` / `exclusion_group_violated` / `conflict_group_violated` |

`AssemblyMaterializer` 在**建卷之前**复验；不通过时 `select` 把运行标 `FAILED`，
issues 写进 `diagnostics.verification`。放在建卷前是因为草稿卷看起来和正常卷子一样，
删它还要牵连 edit_seq 与审核记录。

`test_assembly_pipeline.py` 有一条端到端断言：造一份**自身哈希自洽但分值不符合蓝图**
的方案（绕开"载荷被改过"那道检查），`select` 抛 `SolutionVerificationError`、运行转
`FAILED`、`proxy.created == []`（一份卷子都没建）。

### A/B 配对入口（组卷页）

运行历史里除"当前查看"外的另一次已解出的运行，可以「与本页运行配 A/B」。判定在
服务端（与 `comparison` 同一套 `compare_structure`），前端只负责把结果说清楚：

- 配成功：显示 `已配成 A/B：A / B` + 「结构匹配的 A/B 卷；不代表统计等值」+
  「仍要分别提交审核、分别导出与发布」；
- 配不上：用 `role="alert"` 显示，逐条列出重叠的槽位，**不画成绿色成功**，
  并且仍然声明不代表等值；
- 没有方案、或当前运行自己，不出现配对按钮。

验证：`test-view-paper-assembly.cjs` 81 项通过（新增 7 项配对断言）。



### 为什么求解要走队列

一次 CP-SAT 求解几十秒起步，1,000 候选/50 槽位更久；放在 HTTP 请求里必然超时，
改成"后台线程"又失去重试、心跳与失败可见性（进程重启后连"有没有在跑"都查不到）。
`pipeline_job` 已有状态机、心跳超时回收、重试上限与前端进度轮询，直接复用。

### 交付

- `db/migrations/0035_assembly_job_kind.sql`：`pipeline_job.kind` 增加 `paper-assembly`；
- `server/app/generation.py`：`claim_next()` 白名单同步（两处名单只改一处的结果是
  "任务能入队却永远没人领"——比报错更难发现）；
- `AssemblyService.start(enqueue_only=True)` + `AssemblyService.execute(run_id)`：
  排队路径只建 queued 行并入队；worker 路径幂等执行（**终态不再重解**）；
- `server/app/assembly_worker.py`：`run_job(job)` 调 `execute` 并返回小摘要；
- `POST /assembly-runs` 支持 `enqueue_only=true` → **202**，且响应**不含** `solutions`
  （那时还没求解，给出方案就是骗人）。

### 幂等与防篡改（真实测试）

`server/tests/test_assembly_worker.py`（6 项）：运行仓储是真的，求解器是桩。

- 同一运行被领两次 → 求解器只调用 **1** 次；
- 运行行里的候选清单哈希对不上（有人改过库）→ 记 `FAILED` 且求解器 **0** 次调用；
- 求解器不可用（本机真实状态）→ 记 `FAILED` + 诊断，**不抛异常**拖住队列；
- 不存在运行时 `RunNotFound`；job 缺 `assembly_run_id` 是载荷错误而不是猜一个运行。

### 迁移真引擎断言

`scripts/verify-assembly-job-kind.cjs`（PGlite / PostgreSQL 18.6）：`paper-assembly`
可入队且 `status=queued`、未知 kind 仍被 23514 拒绝、worker 白名单静态核对包含
`paper-render` 与 `paper-assembly`、迁移写法幂等。

`npm run test:migrations`：35/35 迁移、断言 12/12、SQL 级重放 9/9。

### 修掉的真缺陷：接了队列却没写回 job 状态

第一次接线时 `assembly_worker.run_job` 只返回摘要，没有写回 `pipeline_job` 的
`status/finished_at`。后果是一个真实的死循环：任务停在 `running` → 心跳每 15 秒刷
→ 进程退出后 stale 回收重排 → 再领到、再 `running`，队列看起来"一直有活在跑"，
却永远没有结论。

单测当时只断言了**运行行**的状态，没断言 **job 行**的状态，所以没暴露。现在
`test_assembly_worker.py` 用假 db 记录写入，断言 `status=succeeded`、`progress=100`、
`finished_at` 真的被写；`test_worker_describe.py` 另钉住日志措辞（可行但未证明最优
必须写出来，无解不再打印"0 个知识点"）。

另一条约定也写进了测试：求解结论是 `infeasible` 时 **job 记成功**——求解器正常
给出了"无解"这个结论，记成 job 失败会让 worker 反复重试一个已经确定的结果。



### A/B 配对（"跑两次 ≠ A/B 卷"）

`server/app/assembly/ab.py`（8 项测试）+ `GET /assembly-runs/{id}/ab-pair`（5 项 API 测试）。

- 判定顺序：**先比蓝图版本**（版本不同说明分值结构来自不同蓝图，逐槽比较只会给出
  一串"分值不一致"，掩盖真正原因）→ 再比结构 → 最后才谈能不能当 A/B 用；
- 除显式声明的锚题外，共用同一道题或同一族题都拒绝（409 + 问题清单）；
- 配对成功也不改变结论：`statistical_equivalence` 恒为 False，措辞仍是
  「结构匹配的 A/B 卷；不代表统计等值」；
- 本接口**不建卷**：配好对之后仍要分别建卷、分别送审、分别渲染，`next_step`
  字段就是这句话。

### 手工蓝图不再被交给求解器

`blueprint_snapshot` 现在拒绝 `assembly_mode=manual`，并给出可执行的下一步
（另存为 `constraint_assisted`）。在此之前，手工蓝图会被当成单卷求解、解出的卷子
又会在落卷时被"手工蓝图不能声称来自求解运行"挡住——教师白跑一次才看到 409。
组卷页同步：手工蓝图页不出现「开始求解」按钮，改为说明 + 「去建卷页」入口。

`test_assembly_blueprint.py` 20 项、`test-view-paper-assembly.cjs` 69 项通过；

## AI 问答：知识点正文先入库（2026-10-22 第三轮）

用户的提问是「ai问答界面说暂时没有知识片段，但是我们不是有教材知识点吗，是还要继续处理吗」。
查下来不是检索坏了，是**检索的原料是 0 行**：问答只查 `textbook_chunk`，而切片一直
按约定搁着，14 门课一本教材都没入库。知识图谱的 4485 个知识点在另一套表里，从来没进过问答。

按「全部 14 门课都切」的决定，做的是"知识点正文 → 问答语料"这一层。数字如下：

| 指标 | 值 |
| --- | --- |
| 入库课程 | 14 门 |
| 知识点（有正文） | 4485 个 |
| 切成片段 | **4590 块** |
| 重建耗时 | 8.5–14.2 秒（全量） |
| 引用是否带页码 | **不带**，改标「知识点「标题」（完整路径）」 |

为什么不留页码：知识点溯源里写的是"书页197起"，那是章节起页，不是这个知识点所在页。
拿它当引用页码就是给每条回答盖错章，宁可不写。

本轮真跑出来的四个问题（都是拿真课程数据、走真接口）：

| 问题 | 结果 |
| --- | --- |
| 数列上极限的定义是什么（数学分析I） | 命中「上极限」，随后柯西收敛准则、定义、下极限 |
| 最小二乘问题有哪些解法（数值线性代数） | 命中 CGLS、线性最小二乘问题、LSQR、Tikhonov、三种解法的首项工作量 |
| 图神经网络里消息传递是怎么做的（神经网络） | 拒答（这门课确实没有这个概念的知识点） |
| 秋天的银杏叶为什么会变黄（数学分析I） | 拒答 |

拒答这两条不是失败，是要的行为：没有依据就说没有，不猜。

### 调这一层时踩到的三件事（都写进代码注释了）

1. **章节容器抢位**。第一次跑「QR 迭代与同时幂法」，6 条引用里 4 条是同一章的四个片段，
   内容全是"本章包含以下子主题"的链接清单——命中词多，但答不了问题。改成
   `node_kind='knowledge'` 优先，章节降权不排除（有些问题只有章节级内容能命中）。
2. **同一知识点切多块会占满 top-k**。加 `DISTINCT ON (node_id)`，一个知识点只留最相关的一块。
3. **只取 3 字滑窗太窄**。「上极限」被切成「数列上 / 上极限 / 限的定」，命中面很小；
   改成 2 字滑窗（步长 1）+ 4 字窗，并加「至少命中两个词」的证据门槛——
   只命中一个词不算依据。另外片段正文开头补了知识点标题，因为正文里常写"它的"这种指代，
   标题本身才是检索词（问"同时幂法"，正文可能一次都没出现）。

## 检查中修复的问题

1. 输入 Excel 使用合法的 SpreadsheetML 标签前缀，读取库无法直接识别。共用读取器在内存中规范化前缀，源文件不变。

3. 小屏幕隐藏图谱侧栏后，节点点击改为直接打开阅读弹窗。
4. 附件以 Blob URL 下载时，明确提供原文件名，避免丢失标准文件名与扩展名。
5. 本地启动器固定使用 127.0.0.1:8765，避免每次随机端口导致浏览器记录落在不同 origin。
