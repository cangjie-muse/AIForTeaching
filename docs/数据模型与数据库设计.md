# 数据模型与数据库设计

日期：2026-10-20。回答两个问题：**现有内容能不能直接用？存进数据库怎么存？**

## 0. 结论

**内容可以一字不改地直接用，但结构要改 6 处，其中 1 处是硬性的。**

现有 `data/course-*.json` 里的正文（Markdown + `$LaTeX$`）、题干、答案、难度、知识点层级、题目关联，**全部可以直接入库**。我写了 `db/build_seed.py` 跑通了全量转换：14 门课、4485 个节点、4807 道题、5287 条关联、169 个资源，一条内容都没改。

**必须改的是主键。** 实测：4485 个节点里只有 **3909 个唯一 ID**，4807 道题里只有 **4120 个唯一 ID**——508 个节点 ID、614 个题目 ID 在不同课程间重名（`group-ch01` 出现 9 次，`B-ch04-10` 出现 2 次）。现在靠"每门课独立命名空间"规避，一进全局数据库就主键冲突。改法：主键一律 `(course_id, id)`。

## 1. 六处结构改造

| # | 项目 | 现状 | 问题 | 处理 | 改内容？ |
| --- | --- | --- | --- | --- | --- |
| 1 | **主键** | 课程内唯一 | 跨课程重名 508/614 处 | 复合主键 `(course_id, id)`；另加 `course_id \|\| ':' \|\| id` 生成列供跨课程链接 | 否 |
| 2 | **章节** | `level=2` 的节点兼任，`chapterId` 指回自身 | 节点表里混着目录节点，查章节要加 `level=2` 条件 | 提升为 `chapter` 表，**沿用节点 id** | 否 |
| 3 | **冗余数组** | `children[]`、`exerciseIds[]`、`nodeIds[]` 三处冗余 | 双向冗余，改一处忘另一处就冲突 | 删数组，只留 `parent_id` 外键 + `exercise_node` 联结表 | 否 |
| 4 | **关系表** | `relationships` 全是 `contains`，且由 `parentId` 生成 | 存的是可派生数据 | `contains` 改为视图 `v_contains`；`relation` 表只存先修/推导等不可派生的边 | 否 |
| 5 | **溯源** | `exercise.source` / `node.source` 是一大段自由文本 | 无法查询、无法过滤"待核"、无法给页码 | 保留原文 `source_raw`，**新增** `source_book/source_page/source_pdf_page/source_no/provenance` | 否 |
| 6 | **审核状态** | 只有课程级 `reviewStatus`，全站"待教师审核" | 无法逐题审核 | `review_status` 枚举逐条记录 | 否 |

另有两处保留但降级：`path`（冗余标题数组）保留为显示用列；`stats`（聚合数字）不建表，改用视图或查询。

## 2. 实测证据

全部数字来自对 `data/course-*.json` 的扫描，不是估算：

| 指标 | 数值 | 说明 |
| --- | --- | --- |
| 课程 | 14 | |
| 节点行数 / 唯一 ID | 4485 / **3909** | 508 个 ID 跨课程重复 |
| 题目行数 / 唯一 ID | 4807 / **4120** | 614 个 ID 跨课程重复 |
| 章节（level=2） | 173 | 提升为 `chapter` |
| 题目-知识点关联 | 5287 | 进 `exercise_node` |
| 课程资源 | 169 | 进 `course_asset` |
| 根节点 id == 课程 id | 14/14 | 所以根节点必须允许与课程同 id |
| 溯源可解析出精确书页 | 3537 / 4807（74%） | 其余是"书页 1–99"这类整章范围 |
| 溯源可解析出 PDF 页 | 278 / 4807 | 大部分只在整章范围里出现 |
| 溯源可解析出原题号 | 4582 / 4807 | |
| "待核"标记 | analysis 一门 416/416 | 这就是为什么必须有 `review_status` |

**一个必须知道的口径问题**：`node.source` 里写的是"书页1–99、PDF页21–119（章节范围；节点精确页待核）"——这是**章节范围**，不是知识点所在页。直接解析成 `source_page` 会把 99 页都算成同一页。所以解析脚本对范围型文本一律留空，并在 `provenance_note` 写明"页码为整章范围，非题目精确页"。**精确页只能靠教材切片后做锚点，这也是 S1 必须先做切片的原因。**

## 3. 表结构

```
课程内容域
  course ─┬─ chapter ── knowledge_node ─┬─ node_chunk ── textbook_chunk
          │                             ├─ exercise_node ── exercise
          │                             └─ relation（仅不可派生关系）
          └─ course_asset

教材与检索域
  textbook ── textbook_chunk（vector(1024) + hnsw 索引）

教学域
  teaching_class ── enrollment
       └─ assignment ── assignment_item ── exercise
                         └─ submission ── submission_item

AI 与审计域
  ai_conversation ── ai_message ── ai_citation ── textbook_chunk
  model_call（成本计量）    audit_log（谁改了什么）
```

完整 DDL 见 [`db/schema.sql`](db/schema.sql)，可直接执行。关键设计：

### 3.1 复合主键 + 全局句柄

```sql
PRIMARY KEY (course_id, id)
```

将来做跨课程知识联系（"流形"在四门课里的不同讲法）时，需要一个全局稳定的句柄。加一列生成列：

```sql
ALTER TABLE knowledge_node ADD COLUMN global_id text
  GENERATED ALWAYS AS (course_id || ':' || id) STORED;
```

这样既能保持与现有数据完全一致的主键语义，又能在跨课程图里唯一定位。

### 3.2 章节升为一等实体

现有数据里章节是 `level=2` 的节点，`chapterId` 指向自己。数据库里单独建 `chapter` 表并**沿用原节点 id**，好处是：

- 现有 URL（`#/course/analysis/outline`）和前端逻辑不用变；
- `knowledge_node.chapter_id` 有真正的外键约束；
- 章节可以有自己的一行元数据（顺序、教材页码范围），不必挤在节点表。

原 `level=2` 的节点**仍然保留在节点表**（它还承担目录展示与子树统计），只是同时拥有一行 `chapter`。这是冗余，但属于"两份数据都由导入脚本生成"，不会人工改出不一致。

### 3.3 `node_chunk`：整个系统的命门

```sql
node_chunk(course_id, node_id, chunk_id, method, confidence, reviewed_by)
```

没有这张表，问答只能给"模型认为对"的答案；有了它，才能回答"教材第 78 页第 2 段"。`method` 记录锚点是怎么来的（人工/标题匹配/向量最近邻/模型提议），`confidence` 与 `reviewed_by` 支撑"未审核锚点不参与引用"这条规则。

配套视图 `v_anchor_coverage` 直接告诉你每门课的锚点覆盖率——**覆盖率低于阈值（建议 80%）的课程不开放问答**，这是比"先做完再上线"更可控的闸门。

### 3.4 批改：AI 分数与教师分数分列

```sql
auto_verdict, auto_score, auto_evidence   -- AI 建议
teacher_score, teacher_comment, graded_by -- 唯一能进成绩的
```

这不是洁癖。高校场景里，一旦 AI 分数和教师分数存在同一列，出问题时无法追溯是谁定的分。分列之后，"AI 初评 → 教师确认"在数据层就是强制的，不依赖界面自觉。

## 4. 怎么灌数据

```bash
# 1. 起数据库（pgvector 镜像，自带向量扩展）
docker compose up -d db

# 2. 建表（会 drop 并重建 public schema，仅用于初始化）
psql "$DATABASE_URL" -f db/schema.sql

# 3. 从现有 JSON 生成 INSERT 脚本
python db/build_seed.py          # 产出 db/seed.sql，约 12 MB

# 4. 灌入
psql "$DATABASE_URL" -f db/seed.sql

# 5. 对账（数字必须与 JSON 一致）
psql "$DATABASE_URL" -c "
  SELECT '课程' k, count(*) FROM course
  UNION ALL SELECT '章节', count(*) FROM chapter
  UNION ALL SELECT '节点', count(*) FROM knowledge_node
  UNION ALL SELECT '题目', count(*) FROM exercise
  UNION ALL SELECT '关联', count(*) FROM exercise_node;"
```

期望值：14 / 173 / 4485 / 4807 / 5287。

`db/seed.sql` 是生成物，已在 `.gitignore` 中排除——数据源头是 `course-packs/` 与 `data/`，重新生成即可，不入库。

## 4.1 这套 SQL 已经真跑过，不是"看着没问题"

本机没有 Docker 和 PostgreSQL，所以我用 WASM 版 PostgreSQL 16（PGlite）实际执行了 `schema.sql` + 12MB 的 `seed.sql`：

```
$ npm run verify:db

  ✓ chapter            173 / 期望 173
  ✓ knowledge_node    4485 / 期望 4485
  ✓ exercise          4807 / 期望 4807
  ✓ exercise_node     5287 / 期望 5287
  ✓ course_asset       169 / 期望 169
```

这个脚本留在 `db/verify_seed.mjs`，以后改 schema 时用它做回归，**不需要数据库服务**（PGlite 是 devDependency）。局限：PGlite 没有 pgvector，脚本会把 `vector(1024)` 降级为 `jsonb` 并跳过 hnsw 索引——它验证的是结构与数据，不是向量检索。

**验证过程中抓到一个分类 bug**：最初我把"来源文本含'自拟'"一律判为自拟题，结果 225 道教材原题被误判，自拟题虚高到 3505 道。原因是教材原题的解答常写"自拟简解"。修正判据（要求出现"自拟训练题"或"教材页码不适用"）后，真实分布是：

| 来源 | 题数 | 占比 |
| --- | --- | --- |
| 教材原题 `textbook` | 3102 | 64.5% |
| 无法判定 `unknown` | 809 | 16.8% |
| 同事导出表 `colleague-export` | 702 | 14.6% |
| 课程自拟 `self-authored` | 194 | 4.0% |

这个数字对批改模块很关键：**64.5% 的题目能追到教材原题**，剩下 35.5% 的溯源要么是导出表行号（无教材页码），要么根本判不出来——批改时给"参考解答"必须区分这两类，否则会把同事自拟的解答当成教材标准答案。

## 5. 教材上传入口（现在只留钩子）

你说切片以后再做，所以现在落地的是**入口和契约**，不是切片实现：

```
textbooks/                      ← 已 gitignore，永不入库
  analysis/
    chenjixiu-3e-vol1.pdf       ← 命名：<课程id>/<教材短名>.pdf
    chenjixiu-3e-vol1.json      ← 同目录同名元数据（可选）
```

元数据文件格式：

```json
{
  "title": "数学分析",
  "edition": "第三版（上册）",
  "authors": "陈纪修、於崇华、金路",
  "publisher": "高等教育出版社",
  "copyright_status": "internal-only",
  "page_offset": 20,
  "note": "PDF 第 21 页对应书页 1"
}
```

上传后由 `pipeline/probe_pdf.py` 做**入门体检**（这一步现在就能跑）：判断是电子版还是扫描件、页数、每页文字层是否可用、公式密度。体检结果决定后续路线——有文字层走直接抽取，纯扫描件才需要上 OCR。

具体契约见 [`pipeline/README.md`](pipeline/README.md)。

## 6. 与现有前端的关系

不要一次性把前端改成读数据库。三步走，每步都可回退：

| 阶段 | 后端 | 前端 | 风险 |
| --- | --- | --- | --- |
| 1（现在） | 只读 API 上线，`/graph` 返回与 `COURSE_DATA` 同构的 JSON | 仍读 `data/courses.js` | 零 |
| 2 | 同一 API | 逐页切换到 fetch，保留 JSON 作为 fallback | 低，可逐页回滚 |
| 3 | API 为唯一数据源 | 移除 8MB 字面量 | 中，需完整回归 |

阶段 1 的价值是**先让数据在数据库里活起来**（可查询、可审核、可统计），而不动前端一根指头。

## 7. 需要你定的三个问题

1. **embedding 模型与维度**：表里现在写死 `vector(1024)`。若用 OpenAI `text-embedding-3-small`（1536）或 BGE-M3（1024）需要改；建议先定模型再建表，否则要重灌向量。
2. **教材版权范围**：`copyright_status` 默认 `internal-only`。如果学院希望把切片结果开放给校外，需要出版社授权，这不是技术问题。
3. **对象存储**：169 张插图与教材 PDF 放数据库还是放 MinIO/OSS？建议对象存储 + 库内只存哈希与路径（当前设计已按此），否则数据库备份会变得很重。
