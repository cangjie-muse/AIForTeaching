# 数据来源：数据库是唯一真源

这篇文章回答三个问题：页面上的课程内容从哪来、新课程怎么进来、审核与可见范围为什么现在管得到它们。

## 一句话

**数据库是唯一真源。** 页面启动时先问后端「库里有哪些课、哪些已发布」，再按库里的内容渲染。
`data/courses.js`（那个 8 MB 的静态包）只在**后端连不上时**兜底，顶栏会挂一个「离线演示数据」的标签。

## 以前为什么会"改了不管用"

旧的取数顺序是反的：

1. 静态包 `data/courses.js` 是底稿，14 门课、4807 道题全在里面；
2. 后端目录 `/api/v1/catalog` 只返回**已发布**的课，用它**覆盖**同名课程；
3. 剩下没进库、或者进了库但没发布的课，学生端继续用静态包。

后果一：那 12/14 门课在数据库里根本不存在（`/api/v1/courses` 只有 3 门演示课），所以

- 「内容审核」的课程下拉里没有它们 → 没法审；
- 「学生可见范围」管不到它们 → 学生看到的是静态包里的全部内容；
- 老师在线改库、发布课程，学生端也不会有任何变化。

后果二（更隐蔽）：`/api/v1/catalog` 返回的是 `{items: [...]}`，而启动代码拿返回值当数组用
（`items.length` / `items.map`），于是"库里的已发布课程覆盖静态包"那段**从来没有执行过**——
即便如此，页面照样能打开、测试照样全绿。现在拆包在 `js/api-client.js` 里统一做，
并用 `scripts/smoke-boot.cjs` 真发一次请求把它钉住。

## 现在的规则（`js/core.js` 的 `app.applyDbCatalog`）

| 库里有没有 | 有没有发布 | 学生端 | 教师端 |
| --- | --- | --- | --- |
| 有 | 已发布 | 显示，正文用库里的 | 显示 |
| 有 | 未发布 | **不显示** | 目录里单列「建设中（未发布）」 |
| 没有（只在静态包） | — | **不显示** | 不显示（历史上没入库的残留） |
| 后端连不上 | — | 显示静态包 + 顶栏「离线演示数据」 | 同左 |

这样"发布"才是唯一的那扇门：不发布的东西不可能被学生看到，不管它是从哪来的。

## 这 14 门课是怎么入库的

它们是建库之前攒出来的静态包，属于历史内容，需要一次性搬进来。搬完就不需要再搬。

```bash
# 1) 静态包 → SQL（读 data/course-*.json，14 门、4807 题、4485 知识点）
python db/build_seed.py

# 2) SQL → 数据库（会先清空业务表；账号、会话不受影响）
IMPORT_COURSES=1 npm run dev:api
#   它内部依次做：迁移 → import_seed.py db/seed.sql --truncate → mark_imported_courses.py
```

`scripts/mark_imported_courses.py` 是这次迁移的口径，也是一条**可审计的声明**：

- 课程：`review_status = 'published'`，写一条 `publish_event`；
- 题目：`review_status = 'published'` + `human_verified_at/by`（可信等级变成「人工通过」）；
- 每门课一条 `audit_log`，动作 `course.import-trusted`，说明是「迁移导入：沿用既有静态包内容，未逐题重审」。

**为什么不算"重新审一遍"**：这些内容本来就在课上用，逐题重审 4807 道不现实，假装审过更糟。
所以把它记成"迁移确认"而不是"人工逐题审核"——将来有人查这题谁审的，看到的是迁移记录，
不会误认为是某位老师逐题点过的。

生产环境（真 PostgreSQL）不需要 `IMPORT_COURSES`，直接：

```bash
psql "$DATABASE_URL" -f db/seed.sql
python scripts/mark_imported_courses.py
```

## 以后新增课程不需要"导入"这个仪式

正常路径两条，都直接写库：

1. **课程内容 → 导入课程包**：把一个资源包（知识节点 / 知识点 / 习题）解析后落库，`mode=replace` 会把包里没有的旧行标成 retired（不物理删，学习记录还挂着）。
2. **课程内容 → 在线新建/编辑**：直接改库。

新建的课默认 `draft`，学生看不到；教师端在课程中心会看到它躺在「建设中（未发布）」里。
审完、发布之后学生才可见——`POST /api/v1/courses/{id}/publish`。

## 两个接口的分工（别混）

| 接口 | 返回 | 谁看 |
| --- | --- | --- |
| `GET /api/v1/courses` | 库里**全部**课程（含未发布、含计数） | 教师端的课程选择、审核页的课程下拉 |
| `GET /api/v1/catalog` | 只有**已发布**课程 | 学生端目录 |
| `GET /api/v1/catalog/{id}` | 单门已发布课程的完整内容（按可见范围过滤后） | 学生端课程页 |

## 发布之后目录要跟着变

「课程内容 → 发布课程」成功后会调 `A.loadCatalog()` 重新拉一次目录：刚发布的课从
「建设中（未发布）」消失，进入正常列表。否则发布完页面没反应，人会以为没成功再点一次。

## 验证

- `node scripts/test-view-catalog.cjs`（16 项）：静态残留被移除、未发布学生不可见、教师端「建设中」、离线兜底。
- `node scripts/e2e-api.cjs`：课程级发布/撤回、条目级发布、可见范围过滤。
- `node scripts/smoke-boot.cjs`（9 项，需要后端在跑）：用真页面代码跑一遍启动流程，
  对着 127.0.0.1:8000 真发请求，确认 14 门课、349 道题都来自数据库，顶栏没有误报离线。
- 现场验证：`GET /api/v1/courses` 返回 14 门、`GET /api/v1/catalog` 返回 14 门已发布课。
